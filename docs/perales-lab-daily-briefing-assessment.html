Perales Lab Daily Briefing

Assessment of the Mac mini Knowledge Base Application

Assessment date: August 8, 2026 · Repository: /Users/erickperales/Projects/knowledge_base · Read-only assessment

Executive summary

The Mac mini is the authoritative operational host and is suitable for a future Perales Lab Daily Briefing. The existing application already provides most of the reusable knowledge-retention pipeline: domain-aware ingestion, normalization, local Ollama synthesis, confidence scoring, review, source summaries, topic aggregation, concept/entity extraction, Obsidian notes, Git history, and graph-integrity checks.

RSS support exists in code but is not currently ingesting feeds. metadata/feeds.json is absent, and the installed com.kb.feed-poller LaunchAgent repeatedly relaunches the immediately exiting poller. Topic aggregation can also occur before approval, and no locking or transaction layer protects queues, manifests, topic notes, Ollama work, or Git commits.

The cleanest Daily Briefing design is an editorial candidate-and-edition layer in front of the existing KB inbox. Only items explicitly promoted should enter the current KB pipeline.

No files were changed during the assessment itself. The repository was already dirty, including modified AI artifacts and untracked ingestion/report files.

1. Current architecture

Main components

  • dashboard.py: FastAPI dashboard for ingestion, mobile sharing, review, querying, domain selection, topics, concepts/entities, feedback, and purge operations. Uvicorn binds to 0.0.0.0:7842.
  • dashboard/index.html: browser UI.
  • scripts/stage_to_inbox.py: browser, clipboard, feed, and PDF intake adapters.
  • scripts/inbox_watcher.py: polls the inbox every five seconds, normalizes and validates new inputs, queues them, and by default starts full processing.
  • scripts/ingest.py: converts inputs into normalized Markdown and updates the source manifest.
  • scripts/pipeline_run.py: orchestrates synthesis, scoring, aggregation, concept/entity extraction, and index rebuilds.
  • scripts/compile_notes.py, llm_driver.py, and apply_synthesis.py: build prompts, call Ollama, sanitize output, and persist compiled notes.
  • scripts/score_synthesis.py and review.py: confidence scoring and human/automatic review decisions.
  • scripts/topic_aggregator.py and concept_aggregator.py: build canonical topics, concepts, and entities.
  • scripts/index_notes.py and vector_index.py: Markdown and semantic indexes.
  • scripts/domains.py: domain-aware storage routing.

3. RSS ingestion

scripts/feed_poller.py supports RSS 2.0 and Atom 1.0 using Python's standard library. It expects metadata/feeds.json, which is absent on the Mac mini. metadata/.feed-poller-state.json is also absent.

Operational finding: the poller exits immediately when no feeds are configured. Because its LaunchAgent uses KeepAlive, launchd continually relaunches it. It is therefore not checking RSS hourly in practice.

With valid configuration, the default interval is 3,600 seconds. New entries are identified solely by canonical URL membership in metadata/.feed-poller-state.json. This is restart-safe but lacks GUID/Atom ID, normalized URL, content hash, publication watermark, atomic writes, and domain-specific state.

The parser retains title, URL, stripped content, and feed name in memory, but persisted feed JSON contains only:

  • title
  • canonical_url
  • content

Feed name, feed URL, author, publication date, GUID, categories, enclosures, and raw RSS metadata are discarded. Output currently targets the legacy raw/inbox/feeds/, not a domain-specific briefing candidate store.

4. Processing and synthesis

synthesize.synthesize_item() uses compile_notes.build_prompt_pack() to provide canonical identity rules, exact output shape, full source content, grounding instructions, and required lineage. Prompt packs live under metadata/domains/<domain>/prompts/.

llm_driver.call_ollama() sends the prompt to Ollama's streaming /api/generate endpoint using phi4:latest. Temporary output goes to tmp/synthesis-output.md. apply_synthesis.py removes wrapping fences, duplicate front matter, citation artifacts, suspicious lines, and malformed wikilinks before writing a source summary.

score_synthesis.score_synthesis() sends the synthesized note back to the same model. Its self-critique rubric is accuracy 40%, completeness 30%, and clarity 30%. It expects JSON containing a numeric score and reasoning. Failures default to 0.5.

The normal pipeline auto-approval threshold is 0.85. A score at or above it sets review_action: approved, review_method: auto, and approved: true. A notable inconsistency is the standalone scoring CLI's default threshold of 0.0, which can auto-approve every valid score unless an explicit threshold is supplied.

5. Review and retention

Each domain stores an authoritative JSON queue and a generated Markdown view. Entries include source identity, input and normalized paths, adapter, domain, validation results, synthesis/scoring timestamps, confidence data, review action/method, and optional rejection reason.

  • Approve: marks the queue entry approved, patches the source summary to approved: true, and makes it eligible for permanent aggregation.
  • Reject: records the decision/reason and patches the summary to approved: false. Artifacts remain until a separate purge.
  • Purge: explicitly removes rejected material and associated artifacts.

Existing equivalents are: Discard → reject/purge; Promote → approve and aggregate. There is no distinct Reference state.

Approval-boundary defect: pipeline_run.run_for_item() calls topic_aggregator.aggregate_for_source() after scoring even when an item was not approved. The topic aggregator does not verify approval. Concept extraction does verify approved: true. A subsequently rejected source can therefore already have influenced a permanent topic note.

6. Knowledge-base structure and integrity

Raw notes

Raw note front matter can include title, source type, origin, domain, ingestion and publication dates, status, topics, tags, author, language, summary, source ID, canonical URL, related sources, confidence, and license. Bodies use Overview, Source Content, Key Points, Notes, and Lineage sections.

Compiled notes

Source summaries use title, domain, note type, compiled_from, compilation date, topics, tags, confidence, generation method, confidence score, and approval. Topic notes add canonical slug, update/version data, and accumulated sources. Concepts and entities retain source lists, dates, approval, generation method, and entity type where applicable.

Relationships and attribution

Source attribution is represented through canonical URLs, source manifests, Lineage sections, compiled_from, Source Notes, and Obsidian [[wikilinks]]. Topic, concept, and entity registries provide canonical identity mappings.

Integrity tooling

  • Structural and wikilink linting in scripts/lint.py
  • Contradiction candidates via lint.py --contradictions
  • Staleness detection via lint.py --staleness
  • Orphan, source coverage, stub, and gap ranking through scripts/graph_health.py
  • Wikilink injection through scripts/inject_wikilinks.py

Contradictions and stale notes are reported for human action rather than automatically rewritten.

7. Git/Obsidian and runtime boundaries

Safe for read-oriented consumption from other machines

  • compiled/domains/<domain>/topics/
  • compiled/domains/<domain>/concepts/
  • compiled/domains/<domain>/entities/
  • compiled/domains/<domain>/source_summaries/
  • compiled/domains/<domain>/index.md
  • Selected reports and normalized raw notes where full provenance is useful

Mac mini runtime-only/single-writer state

  • Inbox, archive, temporary files, operational logs, virtual environment, and installed LaunchAgents
  • Watcher and feed-poller state
  • Live vector-index updates
  • Future briefing candidates, jobs, locks, and audio artifacts

Review queues, manifests, registries, prompt packs, generated notes, reports, watcher state, and the SQLite vector index are currently tracked to varying degrees. The safest operating model is a single Mac mini writer, with other machines pulling compiled Markdown for Obsidian. Other machines should not push competing edits to generated artifacts without a reconciliation workflow.

8. Concurrency and interference risks

  • The watcher immediately processes valid new items while the scheduled pipeline scans all domains every 30 seconds. Both can observe and process the same pending item.
  • There is no processing claim, owner, lease, per-item lock, or global pipeline lock.
  • Queues, manifests, registries, and poller state use direct write_text(), not atomic replacement or transactions.
  • Concurrent processes can duplicate Ollama calls, overwrite summaries or queues, repeat topic aggregation, collide on index rebuilds, and encounter Git index locks.
  • git_ops.commit_pipeline_stage() has no application-level serialization or retry and can commit another process's staged changes.
  • Briefing generation, KB synthesis, scoring, topic aggregation, lint, queries, and embeddings would share one Ollama daemon without priority or concurrency controls.
  • Dashboard review actions use the same load-modify-save files as background jobs and can lose concurrent updates.

9. Daily Briefing extension points

Reusable

  • RSS/Atom parsing and HTML cleanup
  • Domain routing and feed staging
  • Raw-note normalization and manifests
  • Review UI patterns and audit metadata
  • Source synthesis and confidence scoring
  • Topic, concept, entity, and index generation
  • Obsidian formats and graph-integrity tooling

Needs modification

  • Domain-aware RSS configuration and richer feed metadata
  • GUID/hash-based deduplication and transactional state
  • Hard approval gate before permanent topic aggregation
  • Atomic queue/state writes, job ownership, Git serialization, and Ollama scheduling
  • A Reference outcome distinct from rejection
  • Briefing-aware dashboard review and explicit scoring thresholds

New components

  • Relevance/editorial ranking and daily diversity/selection rules
  • Briefing edition and candidate state
  • Multi-item narrative/podcast prompts
  • Optional TTS and audio storage/publication
  • Per-item Discard, Reference, and Promote controls
  • Briefing history, regeneration, and delivery
  • Shared job locking and inference scheduling

11. Smallest clean implementation

  1. Stabilize the existing Mac runtime: correct the RSS LaunchAgent, add domain-aware feed configuration, enforce approval before topic aggregation, make state writes atomic, and serialize processing/Git operations.
  2. Choose one automatic processing owner. Prefer an ingestion-only watcher plus a serialized job runner, rather than watcher and 30-second pipeline both processing items.
  3. Add a thin briefing candidate/edition store. SQLite is preferable to several concurrently written JSON files.
  4. Keep RSS candidates outside the KB inbox until the user chooses Promote.
  5. Add editorial ranking, daily selection, briefing narrative, and optional TTS as briefing-specific stages.
  6. Represent Reference as retained and searchable but excluded from topic/concept aggregation.
  7. On Promote, call the existing stage_to_inbox.stage_feed() path with richer provenance, then let the existing domain-aware KB pipeline take over.
  8. Record the generated KB source_id back on the briefing item.
  9. Use a shared Ollama job queue/lock and avoid overlapping the briefing window with weekly lint or bulk processing.

The Mac mini remains the right runtime host because it already owns Ollama, launchd scheduling, the authoritative Git checkout, local source data, the dashboard, and the compiled Obsidian knowledge base.
